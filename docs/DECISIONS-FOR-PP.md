# Decisions for pp (smallest reasonable choices made along the way)

## M1
- **libimobiledevice pinned to master (60bf03b, 2026-11-18)**, not the 1.4.0 tag, for current-iOS support. Master requires `libtatsu` (which pulls in libcurl, i.e. network code) only for its CLI tools. We build no tools, and `build-deps.sh` removes the libtatsu configure check. No libcurl/libtatsu ships. Documented in `Contents/Resources/Licenses/VERSIONS.txt`.
- **TLS: OpenSSL 3.5.9 built static** and linked into libimobiledevice, so only four dylibs ship (libplist, libimobiledevice-glue, libusbmuxd, libimobiledevice).
- **Device discovery polls** `idevice_get_device_list_extended` every 2 s (attach/detach events are derived from the diff) instead of `idevice_events_subscribe`. It is simpler and gives USB and Wi-Fi entries per UDID. Can be swapped for events later without UI changes.
- **Reading a device that was never paired** makes libimobiledevice's handshake request pairing, so the iPhone shows its "Trust This Computer?" dialog. We retry only every 30 s while the device is untrusted.
- **Offline check and libc resolver symbols:** `getaddrinfo`/`gethostbyname` are imported by libimobiledevice(-glue)'s generic socket helpers, so the check does not ban them at symbol level. It bans HTTP/URL-loading/curl/Sparkle/CFNetwork/Network.framework linkage and symbols, plus the same APIs in our sources. Real proof is the firewall test planned for M4 (`docs/OFFLINE.md`).
- **Full Disk Access detection:** try to list `MobileSync/Backup`. If it doesn't exist yet, probe `~/Library/Safari` as a TCC indicator. After granting FDA, macOS usually requires restarting the app, which the UI says.
- **Product names:** table covers iPhones (6s to 17 / Air) and iPod touch 7; iPads show just "iPad" for now.
- **Ad-hoc signed** app (`codesign -s -`), so users must right-click → Open the first time.

## M2
- **Own mobilebackup2 loop in Swift.** The protocol logic (`BackupMessageHandler`, `BackupRunner`) is pure Swift behind `MobileBackup2Transport`/`BackupDeviceSession`, tested with a fake device. Only `NativeBackupSession.swift` calls C (lockdown, notification_proxy, AFC, mobilebackup2). `idevicebackup2.c` was read for semantics only; no code copied (GPL).
- **Last Backup Date rule (review finding 1).** Status.plist (`SnapshotState == finished`) is the source of truth. If it exists and is not finished (failed/running backup), nothing counts as a success. Info.plist is only a fallback when Status.plist is missing/unreadable (or finished without a date). Our engine writes Info.plist at the start of a run with the *previous* "Last Backup Date" (Finder writes "now" at the start) and sets the new date only after Status.plist says finished. The GUID and any unknown keys (e.g. the application list written by a Finder backup) are preserved.
- **Info.plist content.** Device fields, `iTunes Files` and `iBooks Data 2` (via AFC), iTunes settings and min iTunes version, like iTunes. We do **not** query installation_proxy/SpringBoard, so `Applications`/`Installed Applications` are empty for a first backup made by this app (existing values from a Finder backup are kept). Finder/Apple Configurator only use these for the app list UI; the device restores from Manifest. Worth a real-device restore check.
- **Incremental, one folder.** Same folder per UDID, no `ForceFullBackup`; the device decides full vs incremental from its Manifest/Status. No snapshots in the MVP.
- **Files from the device are written to `<name>.ibh-part` and renamed when complete**, so a dropped connection or cancel never leaves a truncated file under a real name. Leftover parts of a crashed run are swept at the next start (UDID folder and one level below). We don't touch Status.plist/Manifest.db except when the device sends them.
- **Path safety.** Any device path with `..` is refused (status -1); an absolute prefix is treated as relative to the backup root.
- **"Device busy".** First we peek at the AFC lock `/com.apple.itunes.lock_sync` (about 1 s of retries) *without* sending any notification, so a running Finder sync isn't disturbed. Only if free do we run the normal sequence (syncWillStart → lock → syncDidStart …, 25 × 0.2 s). A held lock → `deviceBusy`.
- **Passcode wait.** "Waiting" starts when the device posts `com.apple.LocalAuthentication.ui.presented`. If no such notification arrives, iOS ≥ 16.1 is assumed to be waiting after 10 s without any message. It ends at the first device message or on `ui.dismissed`. After the configured time (default 5 min, `BackupTarget.passcodeWaitSeconds`, setting UI comes in M3) the run is cancelled with `passcodeTimeout`. Cancel latency can be up to the library's receive timeout (about 10 s) while the device is silent.
- **Cancel from the iPhone** (`syncCancelRequest`) ends the run as "cancelled".
- **Sleep prevention** is one `PreventUserIdleSystemSleep` assertion while at least one backup runs. Notifications use `UNUserNotificationCenter` and are skipped when not running from a `.app`.
- **Logging.** os_log (subsystem `io.github.pislagz.iphonebackuphelper`) plus `~/Library/Logs/iPhoneBackupHelper/iPhoneBackupHelper.log`, rotated at 1 MB, 3 files. "Show Log" reveals it in Finder. Logs contain no backup passwords (we never see one) and the UDID is shortened to 8 characters in engine messages.
- **Device polling during a backup** is not paused (battery/lockdown reads continue every 2 min). Revisit in M4 if it disturbs a backup on real hardware.
- **Not verified on hardware.** CI only runs unit tests with a fake device. Please run the M2 items of the manual checklist (USB + Wi-Fi, encrypted and unencrypted, Finder restore, passcode timeout, Finder-holds-lock).

## M3
- **Defaults for a new device:** automatic backups **off** (opt-in), daily, window 20:00–23:00, min battery 20% (ignored while charging), USB or Wi-Fi, AC power not required, min 10 GB free, min 12 h since last backup, passcode wait 5 min, retry every 30 min inside the window.
- **Frequency semantics.** *Daily* and *weekly* mean "once per calendar day (on the selected weekdays)". A backup at any time that day (Finder included) counts. With a window that crosses midnight, a backup made after midnight counts for the day the window started. *Every N hours* is due N hours after the last successful backup. The min-interval rule applies on top of all three. A missed weekly day is **not** caught up the next day.
- **Window rules.** The window start is inclusive and the end exclusive. Start == end means all day. Wall-clock times that don't exist on a DST jump move forward (a 02:30 start becomes 03:00; a window ending at 02:00 on the spring-forward night ends at 03:00). Times that happen twice use the first one, so the window covers the repeated hour.
- **Decision wording.** `skip` = nothing to do now ("Next: today 20:00–23:00", also used when the min interval or an overdue window blocks). `wait` = due and inside the window but a condition blocks it ("Waiting: battery 14% < 20%"). The menu shows the text for devices with automatic backups on.
- **Unknown values don't block.** If the AC state or free disk space can't be read, those rules are not applied. An unknown iPhone battery level (first probe still running) **does** block when a minimum battery is set.
- **Disk space** (review finding 1): both the mobilebackup2 `GetFreeDiskSpace` reply and the "min free disk" rule use `volumeAvailableCapacityForImportantUsage` (falls back to `systemFreeSize`). Free-space limits are decimal GB.
- **Retries.** A failed, busy, passcode-timeout or user-cancelled attempt blocks the next automatic attempt for the retry interval. This state lives in memory only, so it resets when the app restarts. After our own success the scheduler also remembers the finish time, so a Mac without Full Disk Access (unreadable Status.plist) doesn't back up again every minute.
- **Passcode notifications** (review finding 2): at most one per run, whatever the runner reports. The "Backup started" notification is **off by default** so scheduled runs stay quiet. Each notification kind has its own toggle (General tab), applied by `FilteringNotifier`. A passcode timeout still posts one "failed" notification per attempt; there is no cross-attempt throttle beyond the retry interval.
- **Scheduler triggers:** 1-minute timer, every device-list change (attach, battery, details), settings changes, wake from sleep (immediately and again after 15 s, once usbmuxd has caught up), clock and time-zone changes. Several devices can still back up at the same time; queueing one at a time is M4.
- **Settings storage:** `~/Library/Application Support/iPhoneBackupHelper/settings.json`. Decoding is field-by-field tolerant. A file that can't be parsed is moved to `settings.corrupt.json`.
- **Settings window** is a SwiftUI `Window` scene opened from the menu ("Settings…"), not the `Settings` scene (unreliable for menu-bar-only apps on macOS 13). "Forget device" only works while the device is disconnected (otherwise it reappears at once). It removes the device and its settings, never its backups.
- **Launch at login** uses `SMAppService.mainApp`. It may need approval in System Settings › Login Items for the ad-hoc signed build.
- **Not verified on hardware:** launch at login, the settings window, and the passcode flow on scheduled runs.

## M3 review fixes (done in M4)
- **Wake from sleep (finding 1).** On `didWake` the scheduler **holds automatic starts** (`holdStarts(for: 60)` as a safety limit), the monitor is refreshed immediately and re-probed (`DeviceMonitor.refreshNow`), again after 15 s, and the hold is released 2 s later. Devices that left during sleep are dropped from the list by that refresh, so no backup starts and fails, and no retry interval is created. "Back up now" is not held. During the hold the menu says "Waiting: checking devices after wake-up".
- **Scheduler status (finding 2).** `.run` never stays in the menu: after `controller.start` the text is "Backup in progress" or "Queued: …"; when the controller refuses (not connected, not trusted, no connection, app quitting) the text is its reason ("Waiting: …").
- **Persisted attempt state (finding 3).** New `state.json` next to `settings.json` (`~/Library/Application Support/iPhoneBackupHelper/state.json`): per UDID `lastSuccess` and `lastFailedAttempt`. Written by `BackupController` after each run; the scheduler merges `lastSuccess` with the Status.plist date (the later wins) and uses `lastFailedAttempt` for retry gating. A success clears the failed attempt. "Forget device" also clears it. A corrupt file is moved to `state.corrupt.json`. **Caveat:** if the user deletes the backup in Finder, the stored success date still counts, so the next automatic backup waits for the next due day; "Back up now" always works.
- This replaces the M3 note "retry state lives in memory only".

## M4
- **One backup at a time, globally** (`maxConcurrent = 1`), FIFO queue shared by "Back up now" and the scheduler. A manual request does **not** jump the queue. The "Backup started" notification fires when the backup really starts, not when it is queued. A queued device that is gone or untrusted when its turn comes is dropped (menu shows "the iPhone was not ready when its turn came"); that doesn't count as a failed attempt. The Mac stays awake from the first start until the queue is empty.
- **Result kinds added:** `disconnected`, `diskFull` (both are problems, notify, and delay the next automatic try by the retry interval), `interrupted` (Mac went to sleep, app quit; no notification, **no retry delay**, not a problem).
- **Disconnect mid-backup.** The engine maps a lost connection to `deviceDisconnected`; also, if the monitor shows the device gone for 15 s (grace, so a brief Wi-Fi glitch doesn't abort), the controller cancels the run itself (otherwise a hung Wi-Fi socket would wait for library timeouts). Cleanup is the M2 path: partial `.ibh-part` file removed, sync lock released, Info.plist keeps the previous "Last Backup Date", and a Status.plist that isn't `finished` never counts as a success.
- **Sleep.** On `willSleep` running backups are cancelled (best effort; the Mac doesn't wait for us) and the queue is dropped, with result "interrupted". If the cancel loses the race with the dying connection, the same reason still applies. After wake the scheduler restarts whatever is still due (see the wake hold above). Idle sleep is prevented during a backup, but not lid-close or a forced sleep.
- **Disk full.** (a) Before requesting a backup we refuse with `diskFull` when the backup volume has under **200 MB** free (`BackupRunnerConfig.minFreeBytes`); the device's own `GetFreeDiskSpace` check does the real sizing. (b) A write failing with ENOSPC/EDQUOT mid-run is reported to the device as an error as before and surfaces as `diskFull`. The partial file is removed. Existing backup files are not deleted.
- **Finder sync lock.** Unchanged from M2 (`deviceBusy`, retried after the retry interval). Not shortened for busy results.
- **Quit.** `applicationShouldTerminate` returns `.terminateLater` while a backup runs or waits, cancels everything and waits up to **25 s** for the engines to clean up (cancel latency can be about 10 s while the phone is silent), then quits. If it doesn't stop in time the app quits anyway: the process exit closes the connection (releasing the phone's lock), and leftover `.ibh-part` files are swept at the next start. No confirmation dialog (it would block logout/shutdown). The Quit button's tooltip warns while a backup runs.
- **Local-address guard (offline hardening).** libimobiledevice connects straight to the address usbmuxd reports for Wi-Fi phones, so `CLAUDE.md`'s rule is now enforced in code: before every device connection we re-list the device and refuse unless it is USB or all its network addresses are loopback/link-local/RFC 1918/ULA (`LocalAddressPolicy`, unit-tested). An address we can't parse counts as refused. If this ever hides a legitimate Wi-Fi phone, the log says "ignoring a Wi-Fi device with a non-local address". Please check Wi-Fi discovery on hardware.
- `USBMUXD_SOCKET_ADDRESS` is removed from the environment at launch (libusbmuxd would otherwise honour a remote address).
- **Packaging.** The CI artifact is `iPhone-Backup-Helper.zip` containing `iPhone Backup Helper.app` and `INSTALL.txt` (GitHub wraps it in one more zip when downloading). CI unzips it, verifies signature, architectures and licenses, and runs the offline check on the unzipped app.
- **No license for the project itself yet.** Nothing in the repo says how pp wants to license the app's own code. README says so; the bundled libraries' LGPL/Apache texts ship in the app. Please decide (any choice is compatible with dynamic LGPL linking).
- **Not verified on hardware** (see `docs/TESTING.md`): everything in the robustness list (disconnect, sleep, quit, disk full, Finder lock, queueing), wake handling, the local-address guard with a real Wi-Fi phone, Finder restore of an app-made backup, launch at login, and the firewall test in `docs/OFFLINE.md`.
- **Cancelling a queued backup** counts like cancelling a running one: the menu shows "Backup cancelled" and the scheduler waits for the retry interval before queueing the device again (otherwise the next evaluate would undo the cancel). `cancelAll()` does the same for queued entries. Queue drops for sleep and quit are not recorded, so those backups restart after wake or relaunch.
